# Промт: мост VPM ↔ DashGrid, проверка совместимости и два релиза

Скопировать целиком в новую сессию агента. Промт самодостаточен; он описывает оба
репозитория, контракт, порядок проверки и правила релиза. Работать **в двух репозиториях
последовательно**, не смешивая их коммиты, теги, ключи и артефакты.

---

## Где запускать

Промт требует правок, коммитов, тегов и релизов **в двух репозиториях**, поэтому сессия должна
иметь доступ на запись к обоим:

- лучший вариант — рабочая папка `/Users/nchalex/Documents/deepseek-harness/`, где лежат
  `DashGrid/` и `AAPerformanceMonitor/` (локальная папка VPM; её remote —
  `nchalexz/VAG-PerformanceMonitor`);
- запуск только в DashGrid не даст сделать VPM-часть: правки, тег и релиз VPM не пройдут
  (файловая песочница/workspace). Запуск только в VPM — зеркально: не будет DashGrid-части,
  а сам промт лежит в `DashGrid/docs`;
- если инструмент умеет только один проект, откройте родительскую папку с двумя репозиториями;
  если это невозможно — выполните VPM-этап отдельной сессией, затем вернитесь в DashGrid для
  совместной проверки и двух релизов.

Пути в промте даны от корня **DashGrid**. Из родительской папки используйте
`DashGrid/docs/...` и `AAPerformanceMonitor/app/...`. В каждом репозитории работайте из его
корня, чтобы `./gradlew`, `git` и релизные скрипты видели свой проект.

## Задача

Довести до рабочего состояния связку **VAG Performance Monitor (VPM)** и **DashGrid**:

1. В VPM довести read-only мост телеметрии по контракту v1: в локальной папке он уже начат — проверить, дописать недостающее, закоммитить; если его нет, реализовать.
2. В DashGrid проверить уже реализованный клиент и кокпит на настоящем VPM, исправить
   несовпадения, не сломав существующее поведение.
3. Прогнать тесты и сборки обоих приложений.
4. Проверить совместимость на одном устройстве/эмуляторе по матрице ниже.
5. **Только после зелёных тестов и совместимости** выпустить **два независимых релиза**:
   VPM — в его репозитории, DashGrid — в его. Каждый со своим тегом, APK, SHA-256 и notes.

Если совместимость не достигнута — релизы не выпускать, остановиться и отчитаться с точным
местом расхождения.

## Контракт v1 (не менять без обеих сторон)

| Что | Значение |
|---|---|
| Authority | `io.github.nchalexz.aaperfmon.telemetry` |
| Permission | `io.github.nchalexz.aaperfmon.permission.READ_TELEMETRY`, `protectionLevel="normal"` |
| Метод | `call("snapshot", null, null)` → `Bundle` или `null` |
| Версия | `version = 1` |
| Прочее | только чтение; `query/insert/update/delete` не поддерживаются; `getType` → `null` |

Bundle: `version` (Int), `connection` (`demo`/`connecting`/`connected`/`disconnected`/`error`),
`status` (строка VPM), `source` (необязательно), `updatedAt` (время последнего обновления
значений, не вызова), `signals` (JSON, максимум 128).

Сигнал: `id`, `label`, `value` (готовая строка как в кокпите VPM), `unit` (**единица
отображения**), `raw` (число в тех же единицах отображения, обязательно для стрелки/порогов),
`stale`, `warning` (порог VPM), `category` (`engine`, `temperatures`, `fuel`, `gearbox`, `turbo`,
`diagnostics`).

Порядок: массив сгруппирован по категориям в порядке экрана VPM; внутри категории — порядок
VPM. Сигнал, который VPM показывает в двух вкладках (наддув, MAP, BARO), отдаётся по разу на
каждую категорию; один и тот же `(id, category)` дважды не отдавать.

Провайдер VPM:

- берёт только `Telemetry.state.value`; не вызывает `startService()`, `connect()`, `Elm327`,
  не опрашивает PID;
- не отдаёт историю, настройки, VIN, путь к адаптеру, запись;
- не стартует сервис из чтения;
- `enforceCallingOrSelfPermission(READ_TELEMETRY, …)` в `call` обязателен;
- `TelemetryWidgetProvider` и его настройки не меняются.

Полный текст контракта, тестов и критериев приёмки — в
`docs/VPM_BRIDGE_PROMPT.md`; он должен остаться источником истины. Если при проверке
обнаружится расхождение, менять контракт можно только синхронно в обоих репозиториях с
повышением версии контракта и обновлением обоих тестов.

## Порядок работы

### Этап 1. VPM: мост

1. Открыть репозиторий VPM, прочитать `README`, `CHANGELOG`, `AGENTS.md` (если есть), build-файлы
   и процесс релиза (workflow, fastlane, теги).
2. Реализовать `TelemetryProvider` + `TelemetrySnapshot` по контракту. Ориентиры:
   `telemetry/TelemetryService.kt`, `telemetry/Signal.kt`, `telemetry/SignalCatalog.kt`,
   `cockpit/ui/MetricRegistry.kt`, `cockpit/ui/DashboardScreens.kt`, `widget/WidgetPublisher.kt`.
3. Взять значения и форматирование из `MetricRegistry`/`SignalCatalog`, а не из сырых PID:
   - главный экран: coolant, boost, oil; speed, rpm, gear, fuel.l100_km, fuel.level_pct;
   - категории: `MetricRegistry.category(...)`;
   - `raw` — в единицах отображения (наддув в bar, не kPa);
   - `warning` — порог `MetricSpec`;
   - альтернативные источники (`vag.7e0.11be.oil_temp`, `vag.714.202f.oil_temp`,
     `vag.7e1.210f.gear`) отдавать как обычные сигналы.
4. Добавить permission и `<provider>` в манифест, тесты (`TelemetrySnapshotTest`), короткий
   `docs/DASHGRID_BRIDGE.md`, запись в CHANGELOG, поднять версию VPM (предложение: **0.5.0**,
   versionCode 5 — согласовать с текущей схемой репозитория).
5. Собрать **локальный** APK (пока не публиковать), установить на тестовое устройство,
   проверить:

   ```sh
   adb shell content call \
     --uri content://io.github.nchalexz.aaperfmon.telemetry \
     --method snapshot
   ```

   Ожидается Bundle с `version=1`, `connection`, `status`, `updatedAt`, `signals`.

6. Прогнать тесты и сборку VPM. Не выпускать релиз до совместной проверки (этап 3).

### Этап 2. DashGrid: сверка и правки

1. Открыть DashGrid, прочитать `docs/VPM.md`, `docs/VPM_BRIDGE_PROMPT.md`, `app/src/main/java/net/prototux/aare/vpm/`.
2. Установить локальный APK VPM с мостом на то же устройство и проверить кокпит:
   - на чистой установке DashGrid есть Home + Car; Car = 100 %;
   - живые значения, `LIVE`, `updatedAt` меняется;
   - DEMO: значения VPM с плашкой DEMO, не выдаются за машину;
   - stale/offline: «—», без нулей, стрелка гаснет;
   - уход/возврат на Car, переключение рабочих столов, свайп двух экранов кокпита, вкладки,
     нажатие на прибор;
   - 1920 × 720 и 1280 × 480, день/ночь, RU/EN;
   - в `adb logcat` нет второго `ELM327`/`Obd`-соединения, нет `SecurityException` на
     `READ_TELEMETRY`, нет повторяющейся строки об отсутствии провайдера.
3. Найденные расхождения чинить **в DashGrid**, если это клиент/UI; **в VPM**, если это
   провайдер/формат. Контракт не «подгонять» под реализацию одной стороны.
4. Если DashGrid был установлен до появления permission в VPM: обновить/переустановить DashGrid
   один раз (Android выдаёт normal-разрешение при установке/обновлении запрашивающего
   приложения).
5. Юнит-тесты DashGrid: `VpmSnapshotTest`, `VpmMetricsTest`, `VpmUiStateTest`, пресет
   `WorkspaceModelTest`; полный прогон:

   ```sh
   ./gradlew :aap:test :app:testDebugUnitTest :headunit:test
   ```

### Этап 3. Совместная проверка (до релизов)

Оба APK собраны локально и установлены на одно устройство/эмулятор. Матрица:

| Проверка | Как | Критерий |
|---|---|---|
| Провайдер | `adb shell content call … snapshot` | `version=1`, непустые `signals`, меняется `updatedAt` |
| Живые данные | Car workspace, VPM connected/demo | значения совпадают с VPM, плашка LIVE/DEMO |
| Нет второго OBD | `adb logcat` при открытом кокпите | только VPM держит ELM327; DashGrid не открывает OBD |
| Нет root/Shizuku | устройство без них | кокпит читает провайдер и работает |
| Permission | `dumpsys package io.dashgrid.app` | `READ_TELEMETRY` granted |
| Устойчивость | уйти с Car и вернуться; сменить workspace | кокпит возвращается, телеметрия не рвётся |
| Жесты | свайп Main↔Categories, тап вкладки, тап прибора | работает; свайп рабочих столов DashGrid не сломан |
| Разрешения | 1920×720, 1280×480 | без обрезки значений и вкладок |
| Тема/язык | ночь/день, RU/EN | токены и подписи корректны |
| Отсутствие VPM | удалить VPM | карточка «Установить», без падения |
| VPM без моста | VPM 0.4.1 | карточка «Обновить VPM», без падения |
| Регрессия | OBD-виджет `car`, OBD-приложение, AA-сборка VPM | не изменены и работают |

Сохранить доказательства: `content call`, ключевые строки logcat, скриншоты 1920×720 и
1280×480, количество тестов.

### Этап 4. Релизы (строго после зелёного этапа 3)

Сначала VPM, затем DashGrid — каждый в своём репозитории, со своим тегом и своими ассетами.

**VPM**

- Версия **0.5.0** (versionCode 5) или следующая по схеме репозитория; CHANGELOG, README/docs,
  `docs/DASHGRID_BRIDGE.md`.
- Собрать релизный APK (standard/AA — по процессу VPM), проверить подпись, размер, SHA-256.
- Тег `v0.5.0`, запушить `main` и тег, опубликовать релиз (APK + notes) по workflow VPM.
- Не прикладывать APK DashGrid и наоборот.

**DashGrid**

- Версия **1.3.0**, versionCode **10300** (стабильный, не pre-release); обновить
  `app/build.gradle.kts`, CHANGELOG, README, TESTING, RELEASE_NOTES.
- В RELEASE_NOTES убрать оговорку «живые значения ждут VPM»; описать проверенную связку и
  оставить честные ограничения (реальный head unit и т.д.).
- Собрать: `./gradlew :app:dashgridStandaloneApk`; проверить `versionName=1.3.0`,
  `versionCode=10300`, подпись `CN=DashGrid`, SHA-256.
- Положить APK и `.sha256` в `dist/`; **не создавать** `.prerelease`-маркер (это стабильный
  релиз); закоммитить, поставить тег `dashgrid-v1.3.0`, запушить `main` и тег.
- Workflow DashGrid опубликует stable-релиз; предыдущий `dashgrid-v1.2.0` (test pre-release)
  останется в истории и будет скрыт как draft по правилу workflow.

Если хотя бы один пункт этапа 3 не проходит — **никаких релизов**, отчёт с блокером.

## Правила правок

- Не ломать существующий OBD-виджет/приложение DashGrid, настройки, AA-сборку VPM,
  `TelemetryWidgetProvider` VPM.
- Не добавлять запись/управление адаптером/историю в API моста.
- Не экспортировать `CockpitActivity`; DashGrid не запускает чужой экран.
- Не открывать второе OBD-соединение ни в одном приложении.
- Не менять контракт v1 без синхронного изменения обеих сторон, обоих тестов и повышения
  версии контракта.
- Каждый репозиторий — свои коммиты, теги, ключи и релизные артефакты. Не пушить чужие APK.
- Соблюдать стиль и тесты каждого репозитория; не отключать существующие проверки.

## Критерии готовности

- [ ] `content call` отдаёт контракт v1.
- [ ] DashGrid показывает живые значения VPM; DEMO/stale/offline честные.
- [ ] Второго соединения ELM327 нет.
- [ ] Кокпит работает без root/Shizuku; permission granted.
- [ ] Оба приложения: тесты и сборки зелёные, `lintVital` DashGrid пройден.
- [ ] Совместимость проверена на одном устройстве/эмуляторе, есть доказательства.
- [ ] VPM-релиз `v0.5.0` опубликован со своим APK/SHA.
- [ ] DashGrid-релиз `dashgrid-v1.3.0` (stable) опубликован со своим APK/SHA.
- [ ] Отчёт: что изменено в каждом репо, результаты тестов, матрица совместимости, ссылки на
  релизы, оставшиеся ограничения.

## Отчёт

2. DashGrid: правки, тесты, сборка, тег/релиз, SHA-256.
3. Матрица совместимости: пункт → результат → доказательство (строка лога/скриншот).
4. Что не проверено и почему.
5. Если релиз не выпущен — точный блокер и следующий шаг.
